# 安全与业务修复说明

本文件对应 2026-11-10 审查报告的 20 项发现，以及随后完成的**统一后台账户体系**改造。生产部署采用服务端名片模式，证书仍由 Nginx Proxy Manager 管理。

> **重要变更（统一后台）**：名片与合同已合并到同一个后台 `/admin/*`，使用同一张 `users` 表登录。原「业务员/管理员双口令 + HMAC token + `card_sessions`」与「设备恢复码（`owner_key`）」已整体废弃。下表中涉及口令与恢复码的条目，现状以「统一账户体系」一节为准。

## 统一账户体系（现行）

| 项目 | 现状 |
|---|---|
| 登录 | `/api/auth/login`，账号 + scrypt 密码，返回服务端会话 token（`contract_sessions`，默认 12 小时） |
| 角色 | `admin` 主管理员 / `contract_admin` 合同管理员 / `staff` 业务员，三种角色均可登录 |
| 名片归属 | `cards.owner_user_id` → `users.id`；改派由主管理员在「全部名片 → 改派归属」完成 |
| 配额 | `card_daily_usage(user_id, day_key)`，按账号统计 |
| 存量数据 | 首个管理员创建后，无归属名片自动迁到该账号；短码、正文、头像、创建时间全部保留 |
| 初始化 | `server/sql/init-admin.mjs` 读 `INIT_ADMIN_USER/INIT_ADMIN_PASSWORD`，幂等创建主管理员 |
| 会话撤销 | 退出即撤销当前会话；改密码不强制其他设备下线（如需可后续加） |

一次性迁移（`server/src/db.js` 的 `ensureSchema`，可重复执行）：为 `cards` 补 `owner_user_id` 列与索引、`DROP TABLE card_sessions`、重建 `card_daily_usage`。

## 修复对应表

| 审查项 | 修改 |
|---|---|
| S01 转发头与限流 | API 默认不信任转发头；Docker 显式指定可信代理，项目 Nginx 覆盖转发 IP。限流状态有 TTL 和容量边界 |
| S02 旧口令头 | 已连同口令体系一起移除；所有受保护接口只接受 `Authorization: Bearer <会话 token>` |
| S03 无签名旧名片 | `/card#d=...` 旧链接不再解析，直接提示"未找到该名片"；有效短码也不能被 hash 覆盖 |
| B01 删除失败丢索引 | 仅在删除成功或记录已不存在时移除索引，界面按服务器权限展示操作 |
| S04 停用缓存 | API 与前端请求均不缓存；名片页恢复可见时校验状态，可见期间每 30 秒刷新 |
| S05 会话撤销 | 会话保存在 `contract_sessions`，退出时删除；token 只存摘要 |
| S06 相同口令 | 不再有共享角色口令；每个账号独立密码，创建与重置时校验 ≥8 位 |
| S07 头像规则 | 只接受有限大小的 JPEG/PNG，服务端解码、限像素并重编码为 180px JPEG，不接受外链头像 |
| B02 500 条上限 | 管理列表按服务端搜索与分页，返回真实总数，支持超过 500 条 |
| B03 共享 IP 配额 | 成功登录不占失败预算；建卡配额按**账号**与业务时区持久化统计，IP 另作短时保护 |
| B04 本地分享 | 已移除本地模式，名片一律存服务端，不再有"仅本机预览"分支 |
| B05 我的名片 | 列表从服务器按账号取回，无 20 条截断 |
| C03 长二维码 | 隐藏与可见二维码使用相同的模式与容量保护 |
| D01 Node EOL | Docker 使用 Node.js 24；开发工具需 Node.js 22.12+。Nginx 明确锁定 1.30.6，避免镜像源的移动标签停留在旧版本 |
| D02 依赖公告 | 升级 Vite 8、React Router 7、兼容插件及锁定依赖 |
| D03 假成功 | 部署健康检查失败返回非零状态 |
| D04 明文日志 | 部署仅显示凭据文件位置，不输出密码 |
| D05 初始化恢复 | `bootstrap.py --resume` 使用原配置继续，不重置现有用户密码；先验证凭据再授权 |
| C01 错误处理 | 非法 JSON 为 400，超大请求为 413；健康检查不回传数据库内部错误 |
| C02 空名片入口 | 缺少短码或有效数据时显示无效链接提示，结束加载 |

另增加名片资料编辑：本人或主管理员可修改联系方式、职位与头像，原短码和二维码保持有效。地图导航使用展示的公司地址。

## 权限边界

- 业务员只能编辑、删除**自己名下**的名片；停用/启用同样限本人或主管理员
- 业务员看不到名片列表页（「全部名片」仅主管理员可见），也不能凭公开短码取得管理权限
- 业务员访问他人合同或附件返回 404（不泄露存在性）；合同金额字段对业务员脱敏
- 合同管理员看不到名片功能，也不能新建账号

## 数据迁移与升级

启动会执行可重复的新增迁移：

- `cards` 增加 `owner_user_id`（可空，`INDEX idx_owner_user`），保留现有字段、记录与短码
- 删除历史 `card_sessions` 表；`card_daily_usage` 重建为按账号统计
- 合同侧 `users` / `contract_sessions` / `contract_*` 表结构不变，`users` 成为两端共用账户表

升级前备份数据库与私有 `.env`。升级后旧 token 全部失效，所有人需用新账号重新登录。部署脚本会自动创建主管理员并迁移存量名片归属；如手动部署，执行：

```bash
docker compose -f deploy/docker-compose.yml -f deploy/docker-compose.override.yml exec -T \
  -e INIT_ADMIN_USER=admin -e INIT_ADMIN_PASSWORD='你的密码' api node sql/init-admin.mjs
```

然后执行 `python3 deploy/verify-deployment.py`，在后台「全部名片」核对历史数据的归属是否正确。

`TRUST_PROXY` 必须与实际代理链匹配。Docker 默认信任回环及私有代理网络；最外层代理必须覆盖客户端传入的 `X-Real-IP`，项目 Nginx 会清洗转发链。若共享网络内包含不可信容器，应将 Nginx 的可信来源与 API 配置收紧到实际代理地址。直接运行 API 时默认使用 `TRUST_PROXY=false`。

```bash

```

服务端测试覆盖统一登录、角色 403、归属改派、按账号配额、退出失效与安全回归（35 + 10 + 5 项）；前端测试覆盖分页、401 登出、删除语义、归属改派参数、请求超时与名片页渲染。真实数据库回归入口为 `server/test/mysql-integration.mjs`，只允许显式设置 `RUN_MYSQL_INTEGRATION=1` 且数据库名称符合 `zhongju_test_<随机值>` 的隔离环境。

## 尚需产品决策的能力

账号现在对应到人，但逐人停职撤权、审批流、完整操作审计、软删除恢复、个人信息保留期限以及微信真实设备分享效果，仍需单独设计和验收。

新访问会重新校验名片状态，但已经保存的海报、截图和已展示的联系方式无法远程撤回。可见页面的状态刷新也不等于撤回已经交付给访问者的内容。
